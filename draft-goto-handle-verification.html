Handle Verification Protocol

Abstract

This document defines the Handle Verification Protocol (HVP), the HTTP-level protocol by which a browser obtains a signed Handle Verification Token (HVT) from an issuer attesting that the user controls a handle, and presents it to a verifier. HVP covers two forms of handle: domain handles, such as @alice.example, which are used by the AT Protocol and are being proposed for ActivityPub, and username handles, such as @alice@social.example, which are used by ActivityPub. A handle of either form is verified the same way, whichever ecosystem the user's account belongs to. HVP uses the same three-party model as the Email Verification Protocol ([EVP]), in which the browser intermediates between the verifier and the issuer and hides the verifier's identity from the issuer.¶

This document defines the syntax of handles, their resolution to a unique user identifier and to the issuer authorized to vouch for them (through a DID document for domain handles, and through WebFinger for username handles), the HVT request, the HVT, and the verification of the HVT and its key binding (HVT+KB). The browser API, that is, how the user selects a handle and how the HVT+KB is delivered to the verifier, is defined separately, for example by the W3C IdP Registration API ([IDP-REGISTRATION]).¶

1. Introduction

Social networks built on open protocols let any server host a user's account, and let users bring their own domain name as their identity. The AT Protocol ([ATPROTO]) identifies every user with a handle that is a DNS name, such as @alice.example, which resolves to a stable decentralized identifier (DID). ActivityPub ([ACTIVITYPUB]) identifies users with handles of the form @alice@social.example, which are resolved with WebFinger ([RFC7033]), and the W3C Social Web Incubator Community Group is considering adding domain handles, such as @alice.example, as an alternative ([HANDLES-TF]). The result is an open federation: a website that wants to accept these users cannot know their providers in advance.¶

Email shows that an open federation can still be verified. A verifier accepts an email address at any mail domain without a prior relationship with the domain, and the Email Verification Protocol ([EVP]) lets the verifier check such an address with a signed token. HVP applies that model to handles, in a way that does not depend on which ecosystem the user's account belongs to.¶

1.1. The Problem

A website that wants to let users sign in with a handle today has to integrate with each ecosystem separately. For the AT Protocol, it uses AT Protocol OAuth ([ATPROTO-OAUTH]): it presents a text field for the user to type their handle, resolves the handle to a DID and PDS, discovers the PDS's authorization server, and redirects the user to it. ActivityPub has no common sign-in protocol, so websites typically use the OAuth API of each server implementation. In both cases:¶

  • the user has to know and type their handle, which experience with OpenID 2.0 suggests many users do not;¶
  • the website is identified to the user's authorization server, which learns every site the user signs in to;¶
  • the browser, which often already knows the user's handles, has no role in the flow, unlike in [EVP] and the Email Verification API ([EMAIL-VERIFICATION-API]), which let the browser integrate verification into autofill and form submission, into a JavaScript API, or into FedCM ([FEDCM]); and¶
  • each authorization server and each website implements the protocol independently, and nothing between them checks the result. An authorization server learns whether it interoperates with a website only by testing against that website, so interoperability across many authorization servers and many websites rests on conformance testing and certification rather than on the protocol itself.¶

1.2. Solution

HVP separates the problem into three parts:¶

  1. Syntax (Section 4): what a handle is, in either of its two forms, and how it is written and normalized.¶
  2. Resolution (Section 5): how a handle is resolved to a unique user identifier, checked against the handle, and turned into the issuer that the user has authorized to vouch for it. A username handle is resolved with WebFinger, in a way that is backwards compatible with ActivityPub, and the WebFinger response names the issuer with a handle-issuer link. A domain handle is resolved to a DID or a username handle, in a way that is backwards compatible with the AT Protocol (Section 5.1.2).¶
  3. Issuance and verification: how a browser obtains a Handle Verification Token (HVT) from the authorized issuer, and how a verifier verifies it. This part reuses the token request, key binding, and token format of EVP.¶

Nothing in issuance or verification depends on the form of the handle, or on whether the account belongs to the AT Protocol or to ActivityPub. A verifier that implements HVP accepts all of them.¶

HVP keeps the privacy properties of EVP: the browser intermediates between the verifier and the issuer, so the issuer does not learn which verifier the user is signing in to.¶

1.3. Scope

This document covers two forms of handle: domain handles, which consist of a DNS name alone, and username handles, which combine a user name and a domain. The two forms are resolved differently, each with the mechanism that is already deployed for it, and are verified the same way. See Section 13.1. Email addresses are out of scope: they are verified with [EVP].¶

HVP provides verified identification, for example to sign a user in: it tells the verifier that the user controls a handle, and which unique user identifier that handle resolves to. It does not provide authorization: an HVT grants no access to the user's account, and cannot be used to read or publish content or to act on the user's behalf. A verifier that needs such access continues to use the ecosystem's authorization protocol, such as AT Protocol OAuth ([ATPROTO-OAUTH]), and can use HVP and that protocol together, for example by signing the user in with HVP and requesting authorization later, only when it needs it. See Section 13.5.¶

1.4. Relationship to EVP

HVP reuses the mechanics of [EVP] (the token request, key binding, and token format) with the substitutions described in this document. A browser API can offer both, using EVP for email addresses and HVP for handles.¶

1.5. Relationship to the Browser API

This document specifies the IETF protocol aspects of handle verification: the HTTP-level interactions between the browser, the issuer, and the verifier, and the lookups needed to resolve a handle. How the browser learns about the user's handles, how the user selects one, and how the browser communicates with the verifier are defined separately. The W3C IdP Registration API ([IDP-REGISTRATION]), an extension of FedCM ([FEDCM]), is one such API. See Appendix B.¶

2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

This document uses the following terms:¶

Handle:
A human-readable identifier of a user, displayed with a leading @: either a domain handle or a username handle. A handle is not necessarily permanent: a user can change it. See Section 4.¶
Domain handle:
A handle that consists of a DNS name, such as alice.example, displayed as @alice.example.¶
Username handle:
A handle that consists of a user name and a DNS name, such as alice@social.example, displayed as @alice@social.example.¶
Unique user identifier:
An identifier of the user's account that resolution produces, and that the HVT carries in its sub claim: a DID, or the self link of the WebFinger response of a username handle. Unlike a handle, which can change hands and point to different accounts over time, it identifies one account. It can still change in some cases, for example when an account identified by a self link moves to another server.¶
DID:
A decentralized identifier ([DID-CORE]) that identifies a user's account more permanently than its handle, such as did:plc:bftbdgcbe4zclvpkboe4hleq or did:web:alice.example. A handle resolves to a DID.¶
DID document:
The document that a DID resolves to. It lists the handle that the account claims, the account's services, and, for HVP, its authorized issuer.¶
Authorized issuer:
The issuer identifier that resolution yields for a handle: the one that a DID document names with its HandleIssuer service (Section 5.1.1), or that the WebFinger response of a username handle names with its handle-issuer link (Section 5.2.1). Only the authorized issuer can issue an HVT that a verifier accepts for that handle. A handle has at most one authorized issuer.¶
Issuer:
A service that verifies the user controls a handle and issues HVTs for it, typically the server that hosts the user's account, such as an AT Protocol personal data server (PDS) or an ActivityPub server. An issuer is identified by an issuer identifier (Section 6.1).¶
Handle Verification Token (HVT):
A JWT ([RFC7519]) issued by an issuer that contains a handle, the unique user identifier it resolves to, and the browser's public key. See Section 7.¶
HVT+KB:
An HVT combined with a Key Binding JWT that binds it to a verifier and a session. See Section 8.¶
Verifier:
The party, typically a website, to which the browser presents an HVT+KB, and which verifies it to learn that the user controls a handle. It corresponds to the relying party (RP) of [EVP] and of federated sign-in protocols.¶

3. Protocol Flow

The protocol involves three parties: the verifier, the browser, and the issuer. The following diagram shows the protocol flow:¶

Step                       Verifier     Browser              Issuer
                               |            |                    |
3.1 Handle Discovery           |      [obtain handle from user]  |
                               |            |                    |
3.2 Session Binding            |--- nonce ->|                    |
                               |            |                    |
3.3 Handle Resolution          |   [resolve handle: subject      |
                               |    identifier, issuer]          |
                               |            |                    |
3.4 HVT Request                |            |-- POST /issuance ->|
                               |            |   (handle, did/url)|
                               |            |                    |
3.5 HVT Issuance               |            |<------- HVT -------|
                               |            |                    |
3.6 KB Creation                |        [create KB-JWT]          |
                               |            |                    |
3.7 HVT+KB Presentation        |<-- HVT+KB -|                    |
                               |            |                    |
3.8 HVT+KB Verification [resolve handle;    |                    |
                         verify HVT+KB]     |                    |
¶

The flow is the same as the flow of [EVP], with two differences: the browser and the verifier resolve the handle (Section 5) where EVP looks up a DNS delegation record, and the token is an HVT rather than an EVT.¶

3.1. Handle Discovery

How the browser assembles candidate handles, from its own store, from accounts that an issuer pushes or the browser pulls, or from the user typing one, is defined by the browser API ([IDP-REGISTRATION]) and is out of scope for this document. When the browser starts from text that the user typed, it parses it as described in Section 4.4.¶

3.2. Session Binding

As in [EVP]: the verifier generates a cryptographically random nonce with at least 128 bits of entropy and binds it to a session it has with the browser. How the verifier provides the nonce to the browser is defined by the browser API.¶

3.3. Handle Resolution

The browser resolves the handle as described in Section 5. Resolution produces the unique user identifier and the authorized issuer. The browser fetches the issuer's metadata (Section 6.2). From this point onward, the handle and the unique user identifier are never altered: they are sent byte-for-byte in the HVT request, and returned byte-for-byte in the handle and sub claims.¶

3.4. HVT Request

The browser sends an HVT request to the issuer's issuance_endpoint. The request is the token request of [EVP], with the substitutions listed in Section 6.3.¶

3.5. HVT Issuance

The issuer verifies the request, checks that the browser's cookies represent a signed-in user who controls the handle, and returns an HVT (Section 7) as the value of issuance_token in an application/json response, as in [EVP].¶

3.6. KB Creation

The browser verifies the HVT (Section 7.3), additionally confirming that the handle and sub claims are byte-for-byte identical to the handle and unique user identifier it requested and that the cnf.jwk claim matches the public key it generated. It then creates a KB-JWT and combines it with the HVT as described in Section 8.¶

3.7. HVT+KB Presentation

The browser provides the HVT+KB to the verifier. This mechanism is defined by the browser API.¶

3.8. HVT+KB Verification

The verifier verifies the HVT+KB as described in Section 9. The verifier resolves the handle itself, and does not rely on the browser's resolution. If verification succeeds, the verifier has verified that the user controls the handle in the handle claim, and has learned the user's unique user identifier in the sub claim.¶

4. Handles

A handle takes one of two forms:¶

  • A domain handle is a DNS name, such as alice.example. Domain handles are the handles of the AT Protocol ([ATPROTO-HANDLE]), and the domain-based handles proposed for ActivityPub ([HANDLES-TF]). In DID documents, a domain handle is written as an at URI ([ATPROTO-URI]), at:// followed by the handle, such as at://alice.example, as in the AT Protocol. This document uses that form for domain handles of every ecosystem.¶
  • A username handle is a user name and a DNS name separated by @, such as alice@social.example. Username handles are the handles of ActivityPub, and correspond to the acct URI ([RFC7565]) acct:alice@social.example, which is resolved with WebFinger ([RFC7033]).¶

A handle is displayed with a leading @, as in @alice.example and @alice@social.example, and is carried in the protocol without it.¶

4.1. Domain Handle Syntax

A domain handle, and the domain of a username handle, MUST satisfy the following rules, which are a synthesis of the hostname rules of [RFC1035], [RFC3696] and [RFC3986]:¶

  • The handle contains only ASCII characters, and is at most 253 characters long.¶
  • The handle consists of at least two labels separated by ASCII periods (.). It has no leading or trailing period.¶
  • Each label is between 1 and 63 characters long, and contains only ASCII letters, digits, and hyphens (-). A label does not start or end with a hyphen.¶
  • The last label (the top-level domain) does not start with a digit. As a consequence, IP addresses are not handles.¶

Internationalized domain names are written in their A-label form ([RFC5890]), for example xn--ls8h.example.¶

In ABNF ([RFC5234]), before normalization:¶

handle    = 1*( label "." ) tld-label
label     = alnum [ *61( alnum / "-" ) alnum ]
tld-label = ALPHA [ *61( alnum / "-" ) alnum ]
alnum     = ALPHA / DIGIT
¶

with the additional constraint that the whole handle is at most 253 characters long. A reference regular expression is:¶

^([a-zA-Z0-9]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?\.)+
[a-zA-Z]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?$
¶

(The regular expression is shown on two lines for display; it is a single expression.)¶

The following top-level domains are syntactically valid in a handle, but a handle whose domain ends in one of them MUST fail resolution: .alt, .arpa, .example, .internal, .invalid, .local, .localhost, and .onion. The .test top-level domain MAY be used in development, and MUST fail resolution in production deployments. (The examples in this document use .example and so would fail resolution.)¶

Open Issue: How internationalized handles are displayed, and how homoglyph attacks are mitigated, in coordination with the internationalization work of [HANDLES-TF].¶

4.2. Username Handle Syntax

A username handle consists of a user name, @, and a domain that satisfies Section 4.1. The user name is the userpart of an acct URI ([RFC7565]), and so does not contain @:¶

user-handle = userpart "@" handle
userpart    = unreserved / sub-delims
              0*( unreserved / pct-encoded / sub-delims )
¶

where unreserved, pct-encoded, and sub-delims are defined by [RFC3986], and handle is defined in Section 4.1. The acct URI of a username handle is acct: followed by the handle.¶

4.3. Normalization

Handles of both forms are case-insensitive. The normalized form of a handle is the handle converted to ASCII lowercase. Every handle in this protocol (in the handle claim, and in comparisons) is in normalized form, and every comparison of handles is a byte-for-byte comparison of normalized handles.¶

4.4. Parsing User Input

To parse a handle that a user typed:¶

  1. Strip leading and trailing ASCII whitespace.¶
  2. If the input starts with @ and contains a second @, it is a username handle: remove the leading @, normalize the rest (Section 4.3), and check that it satisfies Section 4.2.¶
  3. Otherwise, it is a domain handle: if the input starts with at://, remove it, or else if it starts with @, remove it; if it then ends with a single /, remove it; normalize the rest, and check that it satisfies Section 4.1.¶

If any step fails, the input is not a handle.¶

Table 1
Input Handle
@Alice.Example, alice.example, at://alice.example alice.example (domain handle)
@Alice@Social.Example alice@social.example (username handle)
alice@mail.example not a handle
https://alice.example/, @192.0.2.1, @com not a handle

A username handle is always typed with its leading @, which distinguishes it from an email address: alice@mail.example is an email address, which a browser API can verify with [EVP], and @alice@mail.example is a username handle.¶

5. Handle Resolution

Resolution takes a normalized handle and produces:¶

  • the user's unique user identifier, which is the subject of the HVT; and¶
  • the authorized issuer for the handle.¶

Username handles are resolved through WebFinger ([RFC7033]) (Section 5.2), and domain handles through a DID (Section 5.1), or, as proposed for ActivityPub, a username handle (Section 5.2.2). In both cases, resolution checks that the handle and the unique user identifier refer to each other, so that a handle cannot claim an account that does not agree to it, and finds the issuer that the user has explicitly authorized.¶

Both the browser and the verifier perform resolution. The browser does it to find an issuer to ask for an HVT; the verifier does it to check that the HVT was issued by an issuer that is authorized for the handle (Section 9).¶

The following rules apply to every resolution step:¶

  • DNS queries use the resolving party's DNS resolver. DNSSEC is not required, but see Section 11.2.¶
  • HTTP requests use the https scheme, MUST NOT include credentials (cookies or HTTP authentication), and SHOULD NOT include a Referer header. When the browser makes them, they SHOULD be made from an opaque origin, so that the servers involved do not learn which verifier the user is visiting.¶
  • Redirects are followed only to https URLs, and at most 5 times for a single request.¶
  • Responses are subject to reasonable limits on size and time, and resolving parties take the precautions of Section 11.8.¶

5.1. Domain Handles

A domain handle resolves to a DID ([DID-CORE]), which is its unique user identifier, and whose DID document claims the handle back and names the authorized issuer. This generalizes the handle resolution of the AT Protocol ([ATPROTO-HANDLE], [ATPROTO-DID]): it uses ecosystem-neutral names for the records that map a handle to its DID, also accepts the names of the AT Protocol (Section 5.1.2), and adds the extraction of the authorized issuer. As proposed for ActivityPub, a domain handle can instead resolve to a username handle (Section 5.2.2).¶

Given a normalized domain handle handle:¶

  1. Handle to DID. Perform the following lookups. A DID MUST use the plc method ([DID-PLC]) or the web method ([DID-WEB]); otherwise fail. If both lookups yield a DID, and the DIDs differ, fail. If either lookup yields a DID, it is the handle's DID. If the lookups name a username handle instead, resolution continues as described in Section 5.2.2. If neither yields anything, the resolving party MUST fall back to the lookups of existing AT Protocol handles (Section 5.1.2), but only if both lookups established that the handle names nothing: that is, if the DNS query returned no TXT record whose value starts with a recognized key, or no record at all, and the well-known request returned a 404 (Not Found) or 410 (Gone) response, or a document with no recognized member. If either lookup failed in any other way, for example because of a DNS server failure, a timeout, or a server error, fail. A resolving party MAY perform the lookups of Section 5.1.2 in parallel with these, to avoid adding a round trip, and use their results only when it falls back. A handle near the 253-character limit cannot use the DNS lookups, because the prefix would push the query name over the limit; the well-known lookups work for such handles.¶

    • DNS TXT record. Query TXT records at the name _handle. handle. A record whose value starts with did= names a DID, in the remainder of the value. Records whose value starts with anything else are ignored, except as described in Section 5.2.2. This method aligns with [RFC1464].¶
    • Well-known document. GET https:// handle /.well-known/handle. A 2xx response with the application/json media type is a JSON object whose did member, if present, names a DID. Other members are ignored, except as described in Section 5.2.2.¶

  2. DID to DID document. Resolve the DID to its DID document ([DID-CORE]), whose id member MUST be identical to the DID:¶

    • For did:plc, GET the DID from a PLC directory, by default https://plc.directory/ followed by the DID.¶
    • For did:web, GET https:// domain /.well-known/did.json, where domain is the method-specific identifier ([DID-WEB]), such as alice.example for did:web:alice.example. A did:web DID with a path is not supported, as in the AT Protocol ([ATPROTO-DID]).¶

  3. Back-link. Find the first element of the DID document's alsoKnownAs array that is at:// followed by a string that satisfies Section 4.1. After normalization, that string MUST be identical to handle. Otherwise fail. This check ensures that a DID document cannot be claimed by a handle that it did not agree to.¶

  4. Issuer. The authorized issuer is the serviceEndpoint of the DID document's HandleIssuer service (Section 5.1.1). If there is none, fail.¶

If any step fails, resolution fails. The unique user identifier is the DID.¶

For example, the handle @samuelgoto.bsky.social resolves as follows at the time of writing, through the AT Protocol names (Section 5.1.2), since it publishes none of the new ones:¶

GET https://samuelgoto.bsky.social/.well-known/atproto-did
  -> did:plc:bftbdgcbe4zclvpkboe4hleq
GET https://plc.directory/did:plc:bftbdgcbe4zclvpkboe4hleq
  -> alsoKnownAs: ["at://samuelgoto.bsky.social"]
¶

so its unique user identifier is the DID did:plc:bftbdgcbe4zclvpkboe4hleq. Its DID document has no HandleIssuer service yet, so it has no authorized issuer. See Appendix A.¶

Because records and members with other keys are ignored, other kinds of records can be added later without affecting resolving parties that do not support them.¶

Open Issue: Other kinds of records could be added later with keys of their own: for example, domain= for another domain handle, resolved recursively and failing when a loop is detected, or email= for an email address verified with [EVP]. A handle could also be allowed to name several identifiers, any one of which proves it; this would require a rule for which unique user identifier an HVT for the handle carries, because each resolves to a different one, and a verifier identifies accounts by it.¶

Open Issue: The SWICG Handles Task Force proposes /.well-known/activitypub-actor, a JSON document that refers to an ActivityPub actor, to resolve domain handles in ActivityPub ([HANDLES-TF]). This document proposes /.well-known/handle and _handle, which refer to a DID or a username handle instead, so that the same names serve every ecosystem. The two need to be reconciled.¶

5.1.1. The HandleIssuer Service

A DID document names the issuer authorized to vouch for its handle with a service ([DID-CORE]) whose id is #handle_issuer, whose type is HandleIssuer, and whose serviceEndpoint is an issuer identifier (Section 6.1):¶

{ "id": "#handle_issuer", "type": "HandleIssuer",
  "serviceEndpoint": "https://issuer.example" }
¶

The service is identified by its id, which can also be written as the DID followed by #handle_issuer, in the same way that the AT Protocol identifies the account's PDS by the id #atproto_pds ([ATPROTO-DID]). Service ids are unique within a DID document ([DID-CORE]), and in did:plc services are stored as a map keyed by id ([DID-PLC]), so a DID document names at most one issuer.¶

If the DID document has no service whose id is #handle_issuer, or that service's type is not HandleIssuer, or its serviceEndpoint is not an issuer identifier, that is, not an https origin with no path, query, or fragment, the handle has no authorized issuer, and HVP cannot be used with it.¶

Because a handle has a single authorized issuer, a change of issuer takes effect at once: as soon as the DID document names a new issuer, HVTs from the previous one no longer verify. This is the same as when a user moves their account to another server.¶

Authorization is always explicit: resolution does not infer an issuer from the account's existing services, such as its AT Protocol PDS (the #atproto_pds service), the PDS's authorization server, or its ActivityPub server. An issuer has to deploy HVP anyway, and requiring the DID document to name it means that a server does not become able to vouch for a handle in a new way, to verifiers it may never have dealt with, without the account's owner opting in. See Section 13.8.¶

A user who moves their account to another server, and whose issuer is that server, updates their HandleIssuer service as part of the move.¶

Open Issue: The name of the DID service type, and whether it should be registered in the W3C DID Extensions registry.¶

Open Issue: Whether a server that the DID document already names, such as the PDS named by the #atproto_pds service, should be an authorized issuer by default, which would let HVP work with existing accounts without changing their DID documents, at the cost of the explicit opt-in.¶

5.1.2. Backwards Compatibility with the AT Protocol

The AT Protocol maps a handle to a DID with a TXT record at _atproto. followed by the handle, and with the well-known URL /.well-known/atproto-did ([ATPROTO-HANDLE]). These names are specific to the AT Protocol. This document defines ecosystem-neutral names, _handle and /.well-known/handle, which take precedence, and falls back to the AT Protocol names when a handle does not publish the new ones, so that every existing AT Protocol handle keeps working.¶

When step 1 of resolution (Section 5.1) falls back, the resolving party performs the following lookups, each of which yields the handle's DID:¶

  • AT Protocol DNS TXT record. Query TXT records at the name _atproto. handle. Ignore records whose value does not start with did=. The DID is the remainder of the value.¶
  • AT Protocol well-known URL. GET https:// handle /.well-known/atproto-did. A 2xx response with the text/plain media type contains the DID, with leading and trailing whitespace removed.¶

If both lookups yield a DID, and the DIDs differ, resolution fails, in the same way that an AT Protocol handle with conflicting _atproto records fails today. If neither yields a DID, resolution fails.¶

As a consequence:¶

  • A handle that is published with the AT Protocol names only, as every AT Protocol handle is today, resolves for every resolving party, without any change.¶
  • A handle that is published with the new names resolves to what they name, whatever the AT Protocol names say. This lets the owner of a handle point it elsewhere, for example to a username handle, without first removing its AT Protocol records.¶
  • Operators of handle domains MAY publish both. AT Protocol software that does not yet support the new names reads only the AT Protocol names, so operators that want the handle to resolve the same way in both SHOULD keep them consistent.¶

Open Issue: Whether, and when, the AT Protocol adopts the new names, and whether resolving parties can eventually stop querying the AT Protocol names. This needs coordination with the AT Protocol community and the IETF ATP working group.¶

5.2. Username Handles

A username handle is resolved with WebFinger ([RFC7033]), in a way that is backwards compatible with how ActivityPub servers already resolve handles to accounts ([MASTODON-WEBFINGER]). Given a normalized username handle handle, whose acct URI is acct: followed by handle:¶

  1. WebFinger. GET https:// domain /.well-known/webfinger?resource= followed by the percent-encoded acct URI, where domain is the domain of the handle, with an Accept header of application/jrd+json. The response MUST have a 2xx status code and contain a JSON Resource Descriptor ([RFC7033]).¶

  2. Subject. The subject of the resource descriptor, converted to ASCII lowercase, MUST be identical to the acct URI. Otherwise fail. A resource descriptor whose subject names a different account only redirects discovery to that account, and does not make handle one of its handles.¶

  3. Unique user identifier. The unique user identifier is the href of the first link whose rel is self and whose href is an https URL. If there is none, fail. For an ActivityPub account, this is the URI of its actor.¶

  4. Issuer. The authorized issuer is the href of the link whose rel is handle-issuer (Section 5.2.1). If there is none, or more than one, fail.¶

  5. Back-link. Check that the server that hosts the account that the unique user identifier refers to agrees that the account has the handle (Section 11.5). This check ensures that a username handle cannot claim an account that did not agree to it:¶

    • If the origin of the unique user identifier is identical to the authorized issuer, the check succeeds without any further request: the issuer is the server that hosts the account.¶
    • Otherwise, GET https:// host /.well-known/webfinger?resource= followed by the percent-encoded unique user identifier, where host is the host of the unique user identifier, with an Accept header of application/jrd+json; a WebFinger resource can be any URI ([RFC7033]). The response MUST have a 2xx status code and contain a JSON Resource Descriptor; the acct URI of the handle MUST be identical, after conversion to ASCII lowercase, to its subject or to one of its aliases; and it MUST have a self link whose href is identical to the unique user identifier. Otherwise fail.¶

If any step fails, resolution fails.¶

The WebFinger request of step 5 costs one request, and uses only WebFinger, so it does not depend on the protocol of the account. Some ActivityPub implementations, such as Mastodon, already answer such requests for the URLs of their accounts, with the account's canonical handle as the subject, including in split domain configurations. A verifier MAY also perform it when the origins are identical.¶

The resource descriptor is served by the handle's domain, but the unique user identifier and the issuer can be on another host. This lets a domain use handles for accounts that are hosted elsewhere. For example, a domain example.com whose website is hosted separately can run an ActivityPub server at social.example.com, and give its users handles such as @alice@example.com (a "split domain" configuration); or a website can be bridged into ActivityPub by a service that hosts its actor. See Appendix A.¶

For example, a username handle @alice@example.com on a split domain could resolve as follows:¶

GET https://example.com/.well-known/webfinger
      ?resource=acct%3Aalice%40example.com
  -> subject: acct:alice@example.com              (subject ok)
     self:    https://social.example.com/users/alice
     handle-issuer: https://social.example.com
User identifier:    https://social.example.com/users/alice
Issuer:             https://social.example.com    (same origin)
¶

5.2.1. The handle-issuer Link Relation

A WebFinger resource descriptor names the issuer authorized to vouch for its handle with a link ([RFC7033]) whose rel is handle-issuer and whose href is an issuer identifier (Section 6.1):¶

{ "rel": "handle-issuer", "href": "https://social.example" }
¶

A resource descriptor names at most one issuer. If it has no handle-issuer link, or its href is not an issuer identifier, the handle has no authorized issuer, and HVP cannot be used with it. The issuer is usually the server that hosts the account, in which case the back-link request is skipped (Section 5.2), but it can be another origin, for example when a server's website and sign-in have moved to a new domain while its accounts keep their original URLs.¶

As with the HandleIssuer service, authorization is explicit: resolution does not infer an issuer from the self link or from any other link. See Section 13.8.¶

5.2.2. Forwards Compatibility with ActivityPub

ActivityPub identifies users with username handles. Adding domain handles to ActivityPub is ongoing work, proposed by the SWICG Handles Task Force ([HANDLES-TF]). This section describes how HVP resolves a domain handle of an ActivityPub account, by aliasing it to the account's username handle, so that such handles can be verified as they are adopted.¶

A domain handle names a username handle, rather than a DID, in the lookups of step 1 of Section 5.1: with a TXT record whose value starts with webfinger=, followed by the username handle, or with the webfinger member of the well-known document. The username handle MUST be written with its leading @, and satisfy Section 4.2 once the @ is removed; otherwise fail. The rules of step 1 apply: if the two lookups name different username handles, compared in normalized form (Section 4.3), or one names a DID and the other a username handle, fail.¶

Given a domain handle handle that names a username handle, resolve the username handle as described in Section 5.2, with one additional check:¶

  • Back-link. The aliases array of the WebFinger resource descriptor of the username handle ([RFC7033]) MUST contain at:// followed by handle, compared after conversion to ASCII lowercase. Otherwise fail. This check ensures that a username handle cannot be claimed by a domain handle that it did not agree to.¶

The unique user identifier and the authorized issuer are those of the username handle. No DID is involved.¶

For example, a user whose account is @alice@social.example, and who wants to use the domain handle @alice.example, publishes a TXT record _handle.alice.example with the value webfinger=@alice@social.example, or the well-known document:¶

GET /.well-known/handle HTTP/1.1
Host: alice.example

HTTP/1.1 200 OK
Content-Type: application/json

{"webfinger": "@alice@social.example"}
¶

Their server also lists at://alice.example in the aliases of the account's WebFinger resource descriptor, next to its handle-issuer link.¶

Open Issue: Whether an ActivityPub account should also be able to resolve its domain handle to a DID, for example to have an identity that survives a move to another server, or to let one DID document, and so one domain handle, serve both the AT Protocol and ActivityPub. ActivityPub implementations do not identify accounts by DIDs today, so a verifier that receives a DID would not necessarily know how to find, or interact with, the ActivityPub account that it belongs to; the DID document could name the actor in its alsoKnownAs, with a check that the actor refers back to the DID ([FEP-C390]).¶

5.3. Caching

A resolving party MAY cache the results of resolution, subject to DNS time-to-live values and HTTP caching rules. A verifier SHOULD NOT cache resolution results for longer than a few minutes when verifying an HVT+KB, because a user who moves their handle to another issuer, or who loses control of it, expects the change to take effect promptly.¶

6. Issuers

6.1. Issuer Identifier

An issuer identifier is an HTTPS origin: the string https:// followed by a host, with no port, path, or trailing slash, for example https://issuer.example. This is the same form as the issuer identifier of [EVP], and for the same reasons: it names the same thing as the iss claim of OpenID Connect and the issuer of [RFC8414], and it can be compared byte-for-byte.¶

Every use of the issuer identity in this document (the authorized issuer that resolution yields, the iss claim of the HVT, the issuer member of the metadata, and the base of the well-known URL) is this origin. Comparisons are byte-for-byte; no scheme defaulting, port normalization, or trailing-slash tolerance is applied.¶

6.2. Issuer Metadata

An issuer serves its metadata at $ISSUER/.well-known/handle-verification, where $ISSUER is its issuer identifier. For https://issuer.example, this is https://issuer.example/.well-known/handle-verification.¶

The metadata document is a JSON object with the following members:¶

  • issuer (REQUIRED): The issuer identifier. It MUST be identical to the issuer identifier that the document was fetched under, and a party that fetches the document MUST reject it if it is not (as in Section 3.3 of [RFC8414]).¶
  • issuance_endpoint (REQUIRED): The URL that the browser sends HVT requests to. It MUST be an https URL that is same site ([WHATWG.HTML]) with the issuer identifier, so that the HVT request carries the cookies of the issuer's site; a party that fetches the metadata MUST reject it otherwise.¶
  • jwks_uri (REQUIRED): The URL of the issuer's JSON Web Key Set ([RFC7517]), used to verify HVTs.¶
  • signing_alg_values_supported (OPTIONAL): As defined by [EVP].¶
  • federations (OPTIONAL): An array of https URLs, each of which identifies a federation that the accounts of the issuer belong to, such as https://atproto.com. HVP does not interpret these URLs, and verification does not depend on them. A browser API uses them to offer a verifier only the handles whose issuers belong to the federations that the verifier asks for (Appendix B).¶

Example:¶

{
  "issuer": "https://issuer.example",
  "issuance_endpoint": "https://issuer.example/hvp/issuance",
  "jwks_uri": "https://issuer.example/hvp/jwks",
  "signing_alg_values_supported": ["Ed25519", "ES256"],
  "federations": ["https://atproto.com"]
}
¶

An issuer that also acts as an EVP issuer serves its EVP metadata and its HVP metadata at their respective well-known paths. It MAY use the same keys for both.¶

Open Issue: Whether requiring the issuance_endpoint to be same site with the issuer identifier is appropriate, and whether [EVP] has, or should have, the same requirement, so that HVP does not diverge from it.¶

6.3. HVT Request

The HVT request is the token request of [EVP], including its use of HTTP Message Signatures ([RFC9421]) and the hwk key scheme, with the following substitutions:¶

  • The browser performs Section 5, not EVP's issuer discovery, to obtain the issuer and its metadata, and sends the request to the issuance_endpoint of the HVP metadata.¶

  • The request body is a JSON object with the member handle, and exactly one of the members did and url:¶

    • handle (REQUIRED): The handle that the user selected, in normalized form (Section 4.3).¶
    • did: The unique user identifier that the handle resolves to, byte-for-byte as resolution produced it, when it is a DID.¶
    • url: The unique user identifier that the handle resolves to, byte-for-byte as resolution produced it, when it is the self link of a username handle.¶
  • The Sec-Fetch-Dest header has the value handle-verification.¶

Example:¶

POST /hvp/issuance HTTP/1.1
Host: accounts.issuer.example
Cookie: session=...
Content-Type: application/json
Sec-Fetch-Dest: handle-verification
Content-Digest: \
    sha-256=:...:
Signature-Input: sig=("@method" "@authority" "@path" \
    "content-digest" "signature-key");created=1792620000
Signature: sig=:MEQCIHd8Y8qYKm5e3dV8y....:
Signature-Key: sig=hwk;kty="OKP";crv="Ed25519"; \
    x="JrQLj5P_89iXES9-vFgrIy29clF9CC_oPPsw3c5D0bs";alg="Ed25519"

{"handle":"samuelgoto.bsky.social",
 "did":"did:plc:bftbdgcbe4zclvpkboe4hleq"}
¶

On receipt of an HVT request, the issuer:¶

  1. Verifies the request headers, the HTTP Message Signature, and the Content-Digest, as in the request verification of [EVP], with handle-verification in place of email-verification as the expected Sec-Fetch-Dest.¶
  2. Verifies that handle satisfies Section 4.1 or Section 4.2 and is in normalized form, that the body has exactly one of did and url, that a did is a syntactically valid did:plc or did:web DID, and that a url is an https URL. If it does not, the issuer returns an invalid_request error (Section 6.3.1).¶
  3. Checks that the cookies represent a signed-in user who controls handle, and whose account is the did or url. If they do not, the issuer returns an authentication_required error.¶
  4. SHOULD resolve handle (Section 5) and check that it is the authorized issuer and that resolution yields the did or url. An HVT from an issuer that is not authorized is rejected by the verifier anyway, so this check is not needed for security, but it avoids issuing HVTs that will fail.¶
  5. Creates an HVT (Section 7.2) and returns it as the value of issuance_token in an application/json response, as in [EVP].¶

6.3.1. Error Responses

The issuer returns the error responses of [EVP] (invalid_request, invalid_signature, authentication_required, and server errors), with the handle member in place of the email member.¶

7. Handle Verification Token (HVT)

The Handle Verification Token (HVT) is a JWT ([RFC7519]) issued by an issuer. It contains a handle, the unique user identifier that the handle resolves to, and the browser's public key.¶

7.1. HVT Structure

7.1.1. Header

  • alg (REQUIRED): The signing algorithm, with the same requirements as the alg of the EVT in [EVP]: a fully-specified identifier, and not none, a symmetric MAC algorithm, or the polymorphic EdDSA.¶
  • kid (REQUIRED): The identifier of the signing key in the issuer's JWKS.¶
  • typ (REQUIRED): hvt+jwt.¶

7.1.2. Payload

  • iss (REQUIRED): The issuer identifier (Section 6.1).¶
  • iat (REQUIRED): The time the HVT was issued.¶
  • cnf (REQUIRED): A confirmation claim ([RFC7800]) containing the browser's public key as a jwk, reproduced from the Signature-Key header of the HVT request with the same members, including its alg.¶
  • handle (REQUIRED): The handle that the user controls, byte-for-byte as it appeared in the HVT request.¶
  • sub (REQUIRED): The unique user identifier that the handle resolves to (Section 5), byte-for-byte as it appeared in the did or url member of the HVT request.¶

Example:¶

{
  "iss": "https://bsky.social",
  "iat": 1792620000,
  "cnf": {
    "jwk": {
      "kty": "OKP",
      "crv": "Ed25519",
      "x": "JrQLj5P_89iXES9-vFgrIy29clF9CC_oPPsw3c5D0bs",
      "alg": "Ed25519"
    }
  },
  "handle": "samuelgoto.bsky.social",
  "sub": "did:plc:bftbdgcbe4zclvpkboe4hleq"
}
¶

7.1.3. Format

As with the EVT, the HVT has a ~ appended to it for compatibility with SD-JWT with Key Binding ([I-D.ietf-oauth-selective-disclosure-jwt]).¶

7.2. HVT Creation

After verifying the request and authenticating the user, the issuer:¶

  1. Constructs the header with alg, kid, and typ.¶
  2. Constructs the payload with iss, iat, cnf (containing the public key from the Signature-Key header, including its alg member), handle, and sub.¶
  3. Signs the JWT with the private key identified by kid.¶
  4. Appends ~ to the signed JWT.¶

7.3. HVT Verification

Both the browser and the verifier verify the HVT:¶

  1. Parse the HVT into its header, payload, and signature.¶
  2. Verify that typ is hvt+jwt, and validate alg and kid as for the EVT in [EVP].¶
  3. Extract the iss, iat, cnf, handle, and sub claims. Verify that handle satisfies Section 4.1 or Section 4.2 and is in normalized form.¶

  4. Resolve handle (Section 5), and verify that:¶

    • the unique user identifier that resolution produces is byte-for-byte identical to sub; and¶
    • iss is byte-for-byte identical to the authorized issuer.¶
  5. Fetch the issuer metadata from iss (Section 6.2).¶
  6. Fetch the issuer's public keys from its jwks_uri, and verify the HVT's signature with the key identified by kid.¶
  7. Verify that iat is within an acceptable time window.¶

The browser additionally verifies that handle and sub are byte-for-byte identical to the handle and unique user identifier it requested, and that cnf.jwk matches the public key it generated. The browser MAY reuse the results of the resolution it performed before the HVT request for step 4.¶

8. Key Binding (HVT+KB)

Key binding is the key binding of [EVP], with the HVT in place of the EVT. The browser creates a KB-JWT whose aud is the verifier's origin, whose nonce is the verifier's session nonce, and whose sd_hash is the hash of the HVT (including its trailing ~), and signs it with its private key. The HVT+KB is:¶

<HVT>~<KB-JWT>
¶

The HVT+KB is compatible with SD-JWT with Key Binding ([I-D.ietf-oauth-selective-disclosure-jwt]), in the same way as the EVT+KB.¶

9. HVT+KB Verification

The verifier receives the HVT+KB, and verifies it by:¶

  1. Verifying the KB-JWT as in [EVP], with the HVT in place of the EVT: its alg matches the alg of the HVT's cnf.jwk, its aud is the verifier's origin, its nonce is the session's nonce, its iat is recent, and its sd_hash is the hash of the HVT.¶
  2. Verifying the HVT as described in Section 7.3, including resolving the handle itself.¶
  3. Verifying the KB-JWT's signature with the public key in the HVT's cnf.jwk.¶

If all verification steps pass, the verifier has verified that the user controls the handle in the handle claim. The verifier SHOULD identify the user's account by the unique user identifier in the sub claim, and treat the handle as a mutable attribute of the account (Section 11.6).¶

The verifier MUST perform its own resolution in step 2, and MUST NOT rely on resolution results provided by the browser. The verifier's resolution is what establishes that the issuer is authorized for the handle.¶

10. Privacy Considerations

10.1. Three-Party Model

As in [EVP], the browser intermediates between the verifier and the issuer. The issuer learns which handle the user is verifying, but not which verifier the user is signing in to, and the verifier learns the handle only after the user has chosen to share it.¶

10.2. Handles Are Public Identifiers

Handles and unique user identifiers are public by design: they are meant to be shared, are the same at every site, and are linked to the user's public activity in the AT Protocol or ActivityPub. A verifier that receives a handle can correlate the user with other verifiers that receive the same handle, and with the user's public activity under that handle. HVP does not change this, and offers no equivalent of the private email addresses of [EVP]. Browser APIs that use HVP should make clear to the user that the verifier will learn their handle and DID.¶

10.3. Resolution Traffic

Resolution consists of DNS queries and unauthenticated HTTPS requests. Unlike the lookup of [EVP], which queries only the email domain and is shared by every user of that domain, every resolution step of HVP is specific to one user: for a domain handle, the DNS name queried is the handle itself, and the DID document is the user's; for a username handle, the WebFinger request names the user. Any party that observes a resolution therefore learns which user is being resolved, and when.¶

When the browser resolves a handle, the DNS resolver and the servers involved (the handle's host, the host of a did:web DID document, the PLC directory for did:plc, the WebFinger server for a username handle, and, when the back-link request of step 5 of Section 5.2 is made, the server that hosts the account) can observe that the user's device is resolving that handle, but not which verifier is involved, because the requests carry no credentials or referrer.¶

When the verifier resolves a handle to verify an HVT+KB, the requests carry nothing that names the verifier either, but they are sent by the verifier itself. The servers involved see the verifier's network address, which they can often attribute to the verifier, for example through reverse DNS or the verifier's hosting provider, or by signing in to a suspected verifier themselves and observing which address resolves their handle. Combined with the per-user nature of resolution, this can let them learn that a particular user signed in to the verifier at that time. When the handle's host, the host of the DID document, or the WebFinger server is also the user's issuer, as is common for handles under a server's domain and for username handles, the issuer can correlate the HVTs it issues with the resolutions that follow, which weakens the property, described above, that the issuer does not learn which verifier the user signs in to. A verifier that goes on to interact with the user's account in the AT Protocol or ActivityPub reveals this anyway.¶

Verifiers can reduce this exposure by:¶

  • caching resolution results within the limits of Section 5.3, which helps for returning users but not for first sign-ins;¶
  • resolving through an intermediary shared by many verifiers, such as a resolution service reached over Oblivious HTTP ([RFC9458]), so that the servers involved do not see the verifier's network address; and¶
  • for did:plc DIDs, maintaining a local copy of the PLC directory, as described below.¶

A browser or verifier can remove the PLC directory from per-sign-in traffic entirely by maintaining a local copy of the directory, ingested through its bulk export endpoint and kept current through its streaming endpoint ([DID-PLC]), and verifying each operation's signatures as it is ingested. Resolving a did:plc DID then consults the local copy and sends no request that reveals which DID is being resolved. This has limits:¶

  • It applies only to the DID-to-DID-document step. The handle-to-DID step still queries DNS records and well-known URLs of the handle's host, which observe the resolution as described above.¶
  • It does not change the trust placed in the PLC directory (Section 11.7): the local copy contains only what the directory chose to publish, in the order it chose.¶
  • It requires storing and continuously ingesting every operation for every DID, which is a significant cost, particularly for browsers on constrained devices and for small verifiers.¶

11. Security Considerations

11.1. Resolution Is Not Authentication

Resolution establishes which issuer is authorized for a handle. It does not establish that the user controls the handle: that is established by the issuer's signature on an HVT, which the issuer produces only after authenticating the user. An attacker who manipulates the browser's resolution can cause the browser to send the user's handle to an issuer of the attacker's choosing, but cannot produce an HVT that the verifier accepts, because the verifier resolves the handle itself.¶

11.2. DNS Spoofing

Resolution of domain handles relies on DNS TXT records, which are not authenticated unless DNSSEC is used. As in [EVP], spoofing the browser's DNS resolution discloses the handle to the attacker but yields no HVT that the verifier will accept, while spoofing the verifier's DNS resolution lets the attacker choose the DID, and therefore the authorized issuer. Verifiers SHOULD use a DNSSEC-validating resolver, and operators of handle domains SHOULD sign their zones. The other resolution steps rely on HTTPS and the Web PKI.¶

11.3. Domain Control Is Handle Control

Every handle rests on control of a DNS name: whoever controls the handle's domain controls its _handle and _atproto records and its well-known URLs, and therefore which DID or username handle the handle resolves to. For a did:web DID on the handle's domain, the same party also controls the DID document, and therefore the authorized issuer. For a username handle, whoever controls the domain controls its WebFinger responses, and therefore which account and which issuer each username handle refers to, within the limits of step 5 of Section 5.2: a handle can name an account on another server only if that account agrees (Section 11.5). This is by design: it is what lets users bring their own domain. It also means that when a domain changes hands, for example when it expires and is registered by someone else, its handle changes hands too. The back-link check means the new owner cannot claim the previous owner's DID, but can point the handle at a DID of their own.¶

11.4. Conflicting Records

A domain handle can be mapped to a DID or a username handle by up to four records (Section 5.1): two with the new names, and two with the AT Protocol names, which are used only as a fallback (Section 5.1.2). Resolution is designed so that the browser and the verifier cannot reach different results for the same handle, and so that an attacker who can block or delay some lookups cannot choose between them:¶

  • Two records with the same names that name different DIDs or username handles cause resolution to fail, rather than letting the result depend on which record a resolving party happened to read.¶
  • The AT Protocol names are used only when the new names have positively established that the handle names nothing. If a lookup with the new names fails for any other reason, resolution fails, rather than falling back. Otherwise, an attacker who can make that lookup fail, for one party but not the other, could make the two parties resolve the handle through different records.¶

An attacker who can block lookups can still cause resolution to fail, but cannot cause it to succeed with a different result. Only the owner of the handle's domain can create records that disagree.¶

11.5. Unique User Identifiers of Username Handles

The WebFinger response of a username handle is controlled by the owner of the handle's domain, and names both the unique user identifier and the issuer. Without a further check, a malicious domain could name another user's account as the unique user identifier, and an issuer of its own choosing:¶

acct:x@evil.example -> self:          https://social.example/users/bob
                       handle-issuer: https://evil.example
¶

Its issuer could then issue an HVT whose sub is Bob's account, and a verifier that identifies accounts by sub would sign the attacker in as Bob. For domain handles, the back-link checks of Section 5.1 and Section 5.2.2 prevent the equivalent attack, in which a domain handle claims another user's DID or username handle. For username handles, step 5 of Section 5.2 prevents it, in one of two ways:¶

  • If the unique user identifier is on the origin of the authorized issuer, the issuer is the server that hosts the account, and a server that issues an HVT for one of its accounts has authenticated that account's user (step 3 of Section 6.3). A domain can at most give its own handles to accounts on that server.¶
  • Otherwise, the back-link check of step 5 of Section 5.2 requires the server that hosts the account to agree that it has the handle. Bob's account does not claim x@evil.example, so resolution fails.¶

11.6. Handle Reassignment

Handles can be reassigned: a domain can expire and be re-registered, and a hosting provider can let a new account take a handle that a deleted account used. Verifiers SHOULD identify accounts by the unique user identifier in the sub claim rather than by the handle claim. A DID survives changes of handle, so a verifier that keys accounts on it is not affected when a handle moves to another account. The unique user identifier of a username handle is the URL of the account on its server, which survives changes of handle that keep the account on the same server, but changes when the account moves to another server.¶

11.7. Trust in the PLC Directory

For did:plc DIDs, resolution trusts the PLC directory to return the current DID document, and therefore the current authorized issuer.¶

Operations in the PLC directory are signed by the account's rotation keys, and the DID is derived from the hash of the signed genesis operation, so the operation log is self-certifying: a resolving party can fetch the log and verify it instead of trusting the directory's rendering of the DID document. Doing so prevents the directory from forging operations, and therefore from naming an issuer that the account's rotation keys did not authorize.¶

Verifying the log does not remove all trust in the directory. As the "PLC Server Trust Model" section of [DID-PLC] states, some trust in the directory is required, and its attacks are limited to:¶

  • Denial of service: rejecting valid operations, or refusing to serve some information about the DID. For HVP, this includes withholding an operation that changes or removes the HandleIssuer service, so that a resolving party keeps accepting HVTs from an issuer that the user no longer authorizes, or withholding an operation that adds one, so that a newly authorized issuer is rejected.¶
  • Misordering: in the event of a fork in the DID document's history, serving the "wrong" fork. For HVP, this determines which HandleIssuer service is in effect.¶

Neither the browser nor the verifier can detect these attacks. Operations are submitted only to the PLC directory, and are not published anywhere else that a resolving party could observe independently: mirrors and replicas obtain their operations from the directory, and the timestamps that the directory assigns to operations, on which the resolution of forks depends, are not signed. Both the browser and the verifier therefore place this trust in the PLC directory, and HVP inherits it for every handle that resolves to a did:plc DID. Handles that resolve to a did:web DID instead rely on the security of the DID's domain, as described in Section 11.2.¶

11.8. Server-Side Request Forgery

Resolution makes a verifier fetch URLs derived from user-controlled input. Verifiers MUST resolve only https URLs, MUST NOT fetch URLs whose host resolves to a loopback, link-local, or private IP address, and SHOULD apply limits on redirects, response size, and time.¶

11.9. Token Confusion

The typ of the HVT (hvt+jwt) is distinct from that of the EVT (evt+jwt), so an HVT cannot be presented as an EVT or the other way around.¶

13. Design Rationale

13.1. Why Two Resolution Mechanisms?

Domain handles and username handles are resolved differently because each already has a resolution mechanism that is deployed. Domain handles are mapped to a DID through DNS or a well-known URL, as in the AT Protocol, which lets a user bring their own domain without running a server. Username handles are mapped to an account through WebFinger, which every ActivityPub server already implements; supporting HVP then requires updating server software, not asking each user to publish DNS records. Both mechanisms produce the same things, a unique user identifier and an explicitly authorized issuer, so issuance and verification are the same for both.¶

For username handles, HVP could instead treat the handle's domain as the issuer, as [EVP] treats the email domain, and skip WebFinger. But in ActivityPub the server that hosts an account is not always at the handle's domain: in a split domain configuration, the handles are at example.com and the server at social.example.com, and a bridging service can host actors for handles at many domains (Appendix A). WebFinger is what tells the two apart, per user, at the cost of one request.¶

13.2. Why Resolve Domain Handles to a DID?

HVP needs three things from the target of a domain handle: a stable identifier for the account, a document that claims the handle back, and a place to name the issuer. A DID provides all three, through its DID document, in a form that is not specific to any ecosystem, and the AT Protocol already resolves domain handles to DIDs. As proposed for ActivityPub, a username handle provides them too, through its WebFinger resource descriptor, so a domain handle of an ActivityPub account can resolve to its username handle without adopting any new identifier (Section 5.2.2).¶

The record names the kind of value in its key, did= as in the AT Protocol, or webfinger=, so that resolution does not have to infer it, and holds a single value rather than a list. Values of other kinds, such as domain handles or email addresses, can be added later with keys of their own, which resolving parties that do not support them ignore.¶

Resolving a domain handle directly to an ActivityPub actor, as [HANDLES-TF] proposes for ActivityPub, would require a third resolution mechanism, with its own back-link and its own way to name the issuer.¶

Only did:plc and did:web are supported, because they are the methods that the AT Protocol uses. Other methods can be added if an ecosystem needs them. A did:key DID, as used by [FEP-C390], is not sufficient on its own: its DID document is derived from the key, and so has no alsoKnownAs to claim the handle back and no services to name the issuer.¶

13.3. Why the Same-Origin Shortcut?

A username handle's WebFinger response is controlled by the handle's domain, which is not necessarily the server that hosts the account it names (Section 11.5). HVP checks the account back with a WebFinger request for its unique user identifier (step 5 of Section 5.2), at the cost of one request. ActivityPub implementations perform an equivalent check by fetching the actor and reading its webfinger property or performing a reverse WebFinger lookup ([MASTODON-WEBFINGER], [FEP-2C59]), which is specific to ActivityPub.¶

In the common case, the issuer is the server that hosts the account, and the unique user identifier is on its origin. The issuer then authenticates the account's user itself, which gives the same protection for the purposes of HVP, so the back-link request is skipped. This covers split domains and bridges (Appendix A).¶

The back-link request is still needed for issuers on another origin (for example, Threads ([THREADS]) gives its users handles such as @zuck@threads.net, whose actors are at https://threads.net/ap/users/..., while its website, where users sign in, has moved to https://www.threads.com; ActivityPub accounts cannot change their URLs without breaking federation, so the natural issuer is on a different site from the accounts it vouches for).¶

Open Issue: At the time of writing, Threads does not answer WebFinger requests for the URLs of its accounts, which the back-link request requires when the issuer is on another origin, and the reference cited for its move to threads.com is its home page rather than an announcement. How Threads, and other services whose accounts are on a different site from where their users sign in, would deploy HVP needs to be investigated, and the reference replaced.¶

13.4. Why New Names for the Handle Records?

The AT Protocol's _atproto record and /.well-known/atproto-did URL are specific to one ecosystem, and an ActivityPub account that published them would appear to be an AT Protocol account. Neutral names let any ecosystem use the same records. The names do not mention DIDs, because they refer to username handles as well as DIDs, and the well-known document is JSON, so that it can carry more information later. Resolving parties fall back to the AT Protocol names when the new ones are absent (Section 5.1.2), so that every existing AT Protocol handle keeps working, and the new names take precedence when present, so that a handle can move to the new names at its own pace.¶

13.5. Why Not OAuth?

AT Protocol OAuth ([ATPROTO-OAUTH]) and the OAuth APIs of ActivityPub servers let a verifier sign a user in, and grant it access to the user's account. But they ask the verifier to present a text field for the user to type a handle, and they reveal the verifier to the user's authorization server. HVP lets the browser offer the user's handles without the user typing them, and keeps the verifier hidden from the issuer. A verifier that needs access to the user's account, and not only proof that the user controls a handle, still uses OAuth.¶

HVP also changes how interoperability is achieved. In OAuth, the authorization server's response goes to the client, and nothing in between checks it: whether an authorization server interoperates with a given client is discovered by testing that pair, and ecosystems with many of each rely on conformance test suites and certification programs. In HVP, the browser verifies every HVT (Section 7.3) with the same checks that a verifier performs, before any verifier receives it, and does not deliver an HVT that fails. An issuer that develops against a browser therefore has an independent verifier in its development loop, and an HVT that the browser accepts is accepted by any verifier that implements Section 9, unless the handle's resolution changes in between. Each issuer and each verifier needs to interoperate only with the browser's verification, rather than each issuer with each verifier.¶

13.6. Why Generalize EVP?

EVP already solves the same problem for email addresses, with a three-party model, proof of possession of a browser key, and a token format compatible with SD-JWT. Reusing it lets verifiers and issuers share code and keys between the two, and keeps the privacy properties. An alternative would be to profile OpenID Connect, but OpenID Connect's redirect-based flow reveals the verifier to the provider.¶

13.7. Why Does the Verifier Resolve the Handle?

The verifier cannot trust the browser's resolution, which could be manipulated, and it cannot trust the issuer to say which handles it is authorized for. Resolving the handle itself is how the verifier checks that the issuer is authorized, in the same way that the verifier looks up the DNS delegation in [EVP].¶

13.8. Why Require an Explicit HandleIssuer Service?

An account already says who hosts it: an AT Protocol account names its PDS, whose authorization server authenticates it, and an ActivityPub account is hosted by the server of its actor. HVP could infer its issuer from them. It does not, for two reasons. First, there is little to gain: an issuer has to deploy HVP's issuance endpoint and metadata anyway, and a server can add a HandleIssuer service to the DID documents of its accounts at the same time. Second, an HVT is a new kind of statement, presented to verifiers through the browser, and a user who authorized a server to host their account, or to sign them in with OAuth, has not necessarily authorized it to make that statement. An explicit service makes the user's opt-in visible in their DID document.¶

An explicit service also lets a user choose an issuer that is not the server that hosts their account, and gives both ecosystems the same way to name it. The handle-issuer link of a username handle is explicit for the same reasons.¶

13.9. Why Define Handle Resolution Here?

Handle resolution is useful outside any one ecosystem. Defining it here, in a form that is shared by the AT Protocol and ActivityPub, makes HVP implementable from this document alone, by verifiers that implement neither protocol.¶

13.10. Why Are Email Addresses Out of Scope?

Email addresses already have a protocol of their own, [EVP], which is further along, has implementations, and has requirements specific to email, such as private email addresses. A browser API can use EVP for email addresses and HVP for handles side by side; the leading @ of a username handle distinguishes it from an email address (Section 4.4).¶

Appendix B. Relationship to IdP Registration

This section is non-normative.¶

The W3C IdP Registration API ([IDP-REGISTRATION]) extends FedCM ([FEDCM]) so that a verifier can request any issuer in an open federation, and the browser keeps a registry of the user's handles. It relates to HVP the way the Email Verification API ([EMAIL-VERIFICATION-API]) relates to EVP: the browser API decides which handles to offer, lets the user register and select them, and delivers the HVT+KB to the verifier, while HVP defines what a handle is, how it is resolved, and how the HVT is issued and the HVT+KB is verified. In particular:¶

  • The IdP Registration API parses and resolves handles as described in Section 4 and Section 5, and treats the authorized issuer of a handle as its identity provider.¶
  • It fetches the issuer metadata (Section 6.2) of the authorized issuer, and reads the accounts_endpoint and login_url that the browser needs to show the user's accounts and let the user sign in from FedCM's well-known file, /.well-known/web-identity, on the issuer's site.¶
  • A verifier asks for handles by federation, such as https://atproto.com. The browser offers the handles whose issuers list that federation in the federations member of their issuer metadata.¶
  • When the user selects an account, the browser obtains an HVT from the issuer with an HVT request (Section 6.3), rather than with FedCM's identity assertion endpoint, which would reveal the verifier to the issuer, creates the KB-JWT (Section 8), and delivers the HVT+KB to the verifier, which verifies it as described in Section 9.¶
